# ARCHITECTURE.md

## Stack

| Layer | Technology |
|---|---|
| Backend | Go (standard library `net/http`; `modernc.org/sqlite` pure-Go driver from Phase 2) |
| Frontend | Svelte 5 + Vite + TypeScript (plain SPA, hand-written router, no SvelteKit) |
| Metadata/index cache | SQLite, via `internal/database` — Phase 2 |
| Media inspection | `ffprobe`, via `internal/media` + `internal/indexer` — Phase 2 |
| Thumbnails + preview sprites | `ffmpeg` (`libwebp` encoder), via `internal/preview` — Phase 3–4 |
| Container remux | `ffmpeg -c copy`, via `internal/preview` — Phase 6 |
| Playback | Native HTML5 `<video>`, direct play only |
| Auth/onboarding state | `DATA_DIR/config.json`, via `internal/settings` — Phase 7 |
| Password hashing / sessions | `golang.org/x/crypto/bcrypt` + HMAC-SHA256, via `internal/auth` — Phase 7 |
| Deployment | One Docker image, multi-stage build |

## Invariants

These hold across every phase; later work must not violate them.

1. **The filesystem is the source of truth.** Nothing in the app's own state overrides what's actually on disk.
2. **SQLite is a disposable index/cache.** Deleting `DATA_DIR/index.db` and restarting recreates an empty schema and a full rescan reproduces every video ID unchanged — verified by `internal/indexer.TestIndexIsDisposable` and manually in Docker (stop container, delete `index.db*`, restart, metadata and IDs come back identical).
3. **Direct play only.** Files are served byte-for-byte with HTTP range support. Nothing is transcoded; files the browser can't decode are reported clearly instead. (Phase 6's container remux is not an exception: `-c copy` repackages existing, already-compatible video/audio streams into a different container without decoding or re-encoding a single frame — a codec the browser can't decode is still never touched.)
4. **Media directories are mounted read-only.** The app never writes into them.
5. **All mutable state lives under `DATA_DIR`** (default `/data`): `index.db`, `cache/thumbs/`, `cache/sprites/`, `cache/remux/`, and — from Phase 7 — `config.json` (server name, auth credentials, per-root display overrides), kept deliberately separate from `index.db` so deleting the disposable index to force a rescan never also erases login/server setup.
6. **Generated assets are never written beside source videos.**
7. **The Go binary serves the built frontend, embedded.** Non-API, non-asset routes return `index.html` so client-side routing survives reloads; in development, Vite proxies `/api` to the Go server.

## Video ID scheme (fixed — do not change)

A video ID is the **base64url encoding (RFC 4648 §5, no padding) of the UTF-8 string `<rootID>/<relativePath>`**, where `relativePath` uses forward slashes and has no leading slash. Root IDs never contain `/`.

- Derived from the filesystem, so it survives deleting and rebuilding the database.
- Renaming or moving a file changes its ID — acceptable, since the filesystem is the source of truth.
- A decoded ID is **untrusted input** and gets the same path validation as any client-supplied path on every request (see `internal/filesystem/id.go`, `DecodeVideoID`).

Implemented in `internal/filesystem/id.go`.

## Security: path handling

Filesystem access is the app's most important security boundary. Implemented in `internal/filesystem/path.go`:

- Clients send only a root ID and a relative path (or a video ID that decodes to the same).
- Every relative path is cleaned (`CleanRelPath`): absolute paths, null bytes, backslashes, and any `..` traversal — including nested/non-obvious forms like `a/../../x` — are **rejected outright**, not silently clamped.
- `Resolve` joins the cleaned path to the configured root, resolves symlinks (`filepath.EvalSymlinks`), and verifies the canonical result is still inside the canonical root before any file is opened or listed.
- A symlink (inside a browsed folder, or as the final path component) that resolves outside the root is rejected — for streaming/`browse`, with `403`; for a plain directory listing entry, by silently omitting it.
- Hidden entries (dotfiles/dotfolders and NAS/OS clutter — `@eaDir`, `#recycle`, `#snapshot`, `$RECYCLE.BIN`, `System Volume Information`, `lost+found`) are filtered in `internal/filesystem/hidden.go`; extend the list there.
- Host absolute paths are never returned in API responses or errors.
- Only the allow-listed video extensions are served through the stream endpoint (`internal/media/video.go`).

The Tailscale/private-LAN boundary is the app's security perimeter. Phase 7 adds one narrow, explicit exception — see "Onboarding, settings, and an access gate" below — a single shared-credential login, not a general auth system; it's a convenience layer on top of the network boundary, not a replacement for it.

## HTTP error shape

All API errors use:

```json
{ "error": { "code": "not_found", "message": "The requested video was not found." } }
```

See `internal/api/errors.go` for the mapping from internal errors to status codes.

## Range streaming

`internal/streaming/stream.go` opens the file read-only and hands it to `http.ServeContent`, which owns all range/conditional-request semantics (`206`, `416` with `bytes */<size>`, `Accept-Ranges`, multi-range requests). No range parsing is hand-rolled. The server sets `Content-Type` explicitly from the extension map first, so `ServeContent` uses it instead of sniffing.

## Index and metadata (Phase 2)

### Schema and migrations

`internal/database` opens `DATA_DIR/index.db` and applies embedded SQL migrations (`migrations/*.sql`, package `migrations`) on every startup via a hand-rolled runner (`schema_migrations(version)` table, files applied in ascending numeric-prefix order, each in its own transaction). No external migration tool — the app only ever migrates forward, so this stays simpler than pulling in a library.

One table, `videos`, keyed by the video ID (the same opaque ID used everywhere else): `root_id`, `rel_path`, `size`, `mtime_unix`, `duration_seconds`, `width`, `height`, `container`, `video_codec`, `audio_codec`, `status` (`ok`/`error`/`pending`), `probe_error`, `indexed_at_unix`. A row only exists once the indexer has visited that file at least once — until then, the API's metadata fields are simply absent, matching the codec-compatibility design exactly (see "Frontend" under Thumbnails below).

The connection uses WAL mode and `busy_timeout=5000`, but `SetMaxOpenConns(1)`: a single shared `*sql.DB` connection serializes all reads and writes through Go's connection pool. This is a deliberate simplicity tradeoff for a single-user homelab app — it avoids `SQLITE_BUSY` entirely without any retry logic, at the cost of API requests briefly queueing behind individual index writes (each one a single fast upsert, not held for the duration of an `ffprobe` subprocess call). Revisit if a future phase's write volume makes this a real bottleneck.

### Indexer

`internal/indexer` walks each root by recursively calling `filesystem.Browse` (the same function `GET /api/browse` uses), so indexing sees exactly what browsing sees — same hidden-entry filter, same symlink safety, no separate traversal logic to keep in sync. For each video file found:

1. `Store.NeedsProbe` checks whether the row is missing, its `size`/`mtime` differ from what's on disk, or it's still `status='pending'` (never actually probed — see below) — if none of those hold, the file is skipped (no `ffprobe` call).
2. Otherwise `ffprobe` runs (`internal/media.Probe`, JSON output via `-show_format -show_streams`) and the result is upserted (`UpsertOK`) or, on failure, the file is still recorded with `status=error` and a `probe_error` message (`UpsertError`) so it isn't retried every scan — only when the file itself changes again.
3. After a root's walk completes, any row for that root whose ID wasn't seen this pass is deleted (`DeleteStale`) — handles deleted and renamed files (a rename is a new ID; the old ID's row is pruned like a deletion).

A scan runs once automatically at startup and otherwise on demand via `POST /api/scan`; `GET /api/scan/status` reports current/last-run counts. `Indexer.TryStartScan` no-ops if a scan is already running rather than overlapping two scans. The scan context is tied to the process's lifetime (cancelled on `SIGINT`/`SIGTERM` in `cmd/server/main.go`), so a long scan doesn't block a graceful shutdown — `ctx.Err()` is checked between files and between folders.

If `ffprobe` isn't on `PATH` at all, the indexer logs one warning at startup and marks every file `status=error` with a clear message, instead of silently producing an index with no metadata.

### API surface

`GET /api/browse` and `GET /api/videos/{id}` gain `duration`, `width`, `height`, `container`, `videoCodec`, `audioCodec` — all `omitempty` pointers, present only when `status=ok`. This is additive; no Phase 1 field changed shape. `internal/api/dto.go` holds the response DTOs (separate from `internal/filesystem`'s plain-listing types) so the enrichment step is one batched `Store.GetMetadataBatch` call per `browse` request, not N+1 queries.

## Thumbnails (Phase 3)

### Schema

Migration `0002_thumbnails.sql` adds `thumb_status` (`pending`/`ok`/`error`, default `pending`) and `thumb_error` to the `videos` table — no new table. `UpsertOK`/`UpsertError` (the Phase 2 indexer's upserts) reset both to `pending`/`NULL` whenever a file's `size`/`mtime` change, since a changed file's old thumbnail no longer corresponds to its content; an unchanged file's upsert is skipped entirely (per `NeedsProbe`), so its thumbnail status is left alone.

Unlike metadata, thumbnail generation **does not require the indexer to have run first**: `Store.SetThumbOK`/`SetThumbError` upsert a minimal row (real `root_id`/`rel_path`/`size`/`mtime_unix`, `indexed_at_unix` left at the sentinel `0`, `status` left at its column default `pending`) if none exists yet. Leaving `status='pending'` is what keeps `NeedsProbe` returning true for that row later, even though its `size`/`mtime` already match the current file — without it, the indexer would wrongly treat a thumbnail-first row as already-indexed and skip it on every future scan, permanently starving it of duration/width/height/codec metadata. `SetThumbOK`/`SetSpriteOK` also accept a best-effort probed duration (falling back to a direct `media.Probe` call when the indexer hasn't supplied one yet) and record it immediately via `COALESCE`, so the duration badge doesn't have to wait for that later indexer pass at all. This decoupling matters because thumbnail generation is triggered by browsing, which can happen before or after any given file's first index scan.

### Cache and worker pool (`internal/preview`)

- One frame per video, WebP, written to `DATA_DIR/cache/thumbs/<hash>.webp`, where `hash = sha256(videoID|size|mtimeUnix)[:32]` — computed from a **live `os.Stat`** of the source file, not trusted DB columns, so the cache key is always correct even if the indexer hasn't caught up yet. A changed file gets a new hash automatically; the old file becomes an orphan (cleanup is Phase 5).
- Seek point is `SeekTime()`: ~25% of duration, halved for clips under 4s, clamped to `[0, duration-0.5]`; falls back to `1s` when duration is unknown. `generate()` runs `ffmpeg -ss <t> -i <input> -frames:v 1 -vf scale=320:-1 -c:v libwebp -f webp -y <tmp>`, writes to a `.tmp-<pid>` file in the same directory, then renames into place — a concurrent reader never sees a partial file. `GenerateWithFallback` retries once at half the original seek time (or `0`) if the first attempt fails, covering short/malformed files.
- A bounded semaphore (`workers`, set to 2 in `cmd/server/main.go`) caps concurrent FFmpeg processes; each is prefixed with `nice -n 15` when the `nice` binary is available (checked via `exec.LookPath`; its absence is not an error, generation just runs at normal priority — no platform-specific `syscall.Setpriority` code, to avoid OS-specific build complexity for a "nice to have" priority hint).
- Per-video jobs are deduplicated (`Manager.inflight`, keyed by video ID) so a folder-view enqueue and a direct thumbnail request for the same video share one job rather than racing two FFmpeg processes on the same file.
- `Manager.Request(..., wait bool)`: `wait=false` (folder-view lazy enqueue via `EnqueueFolder`) starts a job if needed and returns immediately — browsing is never blocked on FFmpeg. `wait=true` (the `GET /api/videos/{id}/thumbnail` handler) blocks up to 6s for the job to finish, then falls back to "not ready" rather than hanging a request indefinitely. A file whose `thumb_status` is already `error` short-circuits immediately without touching the worker pool at all — a broken file is not retried on every page view.
- Jobs run against `Manager.baseCtx` (the app's lifetime context, same pattern as the Phase 2 indexer's scan context), not the triggering request's context — a job one request started must keep running for other waiters (or the next `browse` call) even if that original request's connection closes.

### API surface

- `GET /api/videos/{id}/thumbnail` — serves the cached WebP (`Cache-Control: public, max-age=31536000, immutable`, safe because the URL's underlying file is content-hash-named) or `404`/`503` (permanently failed / still generating).
- `GET /api/thumbnails/status`, `POST /api/thumbnails/pregenerate` — mirror the Phase 2 scan-status/rescan pair, but for thumbnails; `GetThumbCounts` aggregates via one `GROUP BY thumb_status` query.
- `GET /api/browse` gains `?flatten=true` (recursive listing, answered from the index via `Store.QueryVideosUnderPath` — a prefix `LIKE` query with `%`/`_` properly escaped, since folder names routinely contain literal underscores — never a filesystem walk — this deliberately uses the index, not a live directory scan) and `?sort=name|modified|duration|size` (`internal/api/sort.go`; missing duration/size always sort last, independent of direction). Flattened video entries carry a `subfolder` field (the video's folder path relative to the browsed path) for the UI's secondary-text display. A file not yet indexed simply doesn't appear in the flattened view until a scan reaches it — browsing itself (non-flattened) is unaffected.

### Frontend

- View mode (`grid`/`list`/`large`) and sort key live in the URL as `?view=`/`?sort=` query params (defaults omitted to keep plain folder links clean), alongside `?flatten=true` — same "state lives in the URL" principle as the folder path itself. `BrowseGrid` (grid/large, same cards at different column widths) and the new `BrowseList` (list, via `VideoRow`/`FolderRow`) are separate small containers per the Phase 1 design note, so adding list mode didn't require reworking `Browse.svelte`.
- `VideoCard`/`VideoRow` lazy-load (`loading="lazy"`) an `<img>` pointed at the thumbnail endpoint, layered over the existing placeholder icon; `onerror` just leaves the placeholder showing — a missing/not-yet-generated thumbnail degrades gracefully, never a broken-image icon.
- Codec compatibility (`src/lib/codec.ts`): `HTMLVideoElement.canPlayType()` with a MIME type from the file extension, plus a `codecs` parameter built from a small `videoCodec`/`audioCodec` → codec-string lookup table when ffprobe data is available. Only a confident `''` (definitely not playable) shows the badge — `'maybe'`/`'probably'` both count as playable, since browsers are often deliberately vague. The badge never hides the file — it's a warning, not a filter.

## Preview sprites (Phase 4)

### Schema

Migration `0003_sprites.sql` adds `sprite_status`/`sprite_error`, mirroring `thumb_status`/`thumb_error` exactly (same reset-on-file-change behavior in `UpsertOK`/`UpsertError`, same minimal-row upsert in `SetSpriteOK`/`SetSpriteError` so generation doesn't require the indexer to have run first).

### One shared worker pool, not two

Thumbnails and sprites are generated by the **same `preview.Manager`, same semaphore**. The package was renamed from `internal/thumbnail` to `internal/preview` specifically for this — a second, independent pool for sprites would have let total FFmpeg concurrency exceed the configured bound, defeating the reason the pool exists (never compete with an actively streaming video). `ensureJob` keys are prefixed (`"thumb:<id>"` vs `"sprite:<id>"`) so a thumbnail job and a sprite job for the same video dedupe independently while still drawing from one semaphore.

### Generation: sequential per-frame extraction, not simultaneous — this mattered in practice, not just in theory

Frame count and interval: a nominal ~15s interval is clamped to a [20, 150]-frame budget, then the interval is **recomputed from the clamped, grid-rounded count** so frames always span the video's *entire* duration — the budget limits sprite sheet size/cost, never how much of the video it covers. A naive "fixed interval, stop once you hit the cap" implementation would silently truncate anything over ~37 minutes to a preview of only its first part. `ComputeSpriteLayout`/`TestComputeSpriteLayoutCoversFullDuration` in `internal/preview/layout_test.go` exist specifically to catch that regression.

The first implementation extracted all frames in **one** ffmpeg invocation — many `-ss`/`-i` pairs feeding an `xstack` filter graph, all seeked and decoded *simultaneously*. It worked, and was fast (~12s for 100 frames from a 23-minute 1080p file) — on a MacBook. Tested against the same file in a Docker container with **no memory limit set** and 7.6 GB free, it failed every time with `signal: killed`. Up to 150 concurrent H.264 decode contexts, each buffering its own reference frames for a 1080p stream, spiked memory enough to get OOM-killed — invisible in `docker stats` afterward since the process was already dead by the time anyone looked. This is exactly the class of environment this app targets — low idle CPU and memory on modest homelab hardware, not a beefy dedicated media server — so it wasn't an acceptable "works on my machine" tradeoff.

The fix (`internal/preview/sprite.go`): extract frames **one at a time** — each its own fast, independent `-ss`-before-`-i` seek to a temp PNG, at most one decode context live at any moment — then a separate, cheap final ffmpeg pass reads the small pre-scaled PNGs back via the `image2` sequence input and assembles the grid with the `tile` filter. Verified against the same real file in the same constrained container: succeeded reliably, and — despite trading one ffmpeg invocation for `frameCount + 1` — actually completed *faster* in practice (~12s for all 6 test videos combined, including the 23-minute file), since each single-frame extraction is as cheap as Phase 3's thumbnail generation.

`Manager.Status`/`SpriteStatus`'s `activeWorkers` reports the semaphore's actual held-slot count (an atomic counter incremented/decremented in `acquire`/`release`), not `len(inflight)` — the latter includes jobs merely queued and dispatched, not yet holding a slot, and briefly showed misleadingly high numbers (6, against a configured bound of 2) before this was caught in the same Docker testing pass.

### API surface

- `GET /api/videos/{id}/sprite` (image) and `GET /api/videos/{id}/sprite.json` (metadata: `tileWidth`/`tileHeight`/`columns`/`rows`/`duration`/`frames[]`, each frame's `time` + `{x,y,width,height}`) — same not-ready/permanently-failed response pattern as the thumbnail endpoint, same aggressive immutable caching (content-hash-named files).
- `GET /api/sprites/status`, `POST /api/sprites/pregenerate` — mirror the thumbnail pair exactly.

### Frontend — three surfaces, one asset, two real bugs caught by testing in a browser rather than just reading the code

`src/lib/sprite.ts` picks a frame by fractional position (frames are evenly spaced by construction, so this is index arithmetic, no time-based search) and computes a **percentage-based** CSS background position/size (`background-size: cols*100% rows*100%`, position as `%`) rather than pixel offsets — the standard responsive CSS-sprite technique, needed because each card renders the sprite at a different size than its native tile dimensions.

- **`ScrubPreview.svelte`** (desktop hover + mobile touch-drag on `VideoCard`/`VideoRow`) and **`TimelineScrubber.svelte`** (the player's scrub strip) both fetch sprite metadata lazily, on first interaction. Both had the same bug: the fetch is async, and a hover/touch that arrives and then *holds still* (one `mouseenter` + one `mousemove`, no further motion) can have its single `mousemove` run and bail with `meta` still `null`, then the fetch resolves with nothing left to trigger a re-render — the preview would just never appear unless the pointer happened to move again. Fixed by remembering the last pointer position and rendering once as soon as the fetch lands, gated to the mouse-hover path only (not touch, where the same fix risked flashing a preview frame mid-tap before a drag-vs-tap gesture is even decided).
- **`ScrubPreview.svelte`**'s touch handling needed `preventDefault()` on `touchmove` (block page scroll once a drag is recognized) and `touchend` (suppress the synthetic click that would otherwise also navigate). Bound via Svelte's template event attributes (`ontouchmove={...}`), both calls were silently no-ops — confirmed via the browser's own console warning ("Unable to preventDefault inside passive event listener invocation"), from Svelte 5's event delegation registering the listener as passive. On a real device this would have meant page-scroll during every drag and unwanted navigation after every scrub. Fixed by attaching those two listeners manually via `element.addEventListener(..., {passive: false})` in an `$effect`, bypassing Svelte's template binding for just those two events. `touchstart` (which never calls `preventDefault`) stays template-bound; `mousemove`/`mouseenter`/`mouseleave` are unaffected since the passive default only applies to touch/wheel events. Neither bug was reachable by static analysis or `svelte-check` — both needed the app actually open in a browser tab with real interaction.
- **Player timeline preview** (`TimelineScrubber.svelte`): the native `<video controls>` seek bar (used since Phase 1) has no scriptable position — it varies by browser/OS/zoom and isn't exposed to CSS or JS. Rather than guess and risk a preview overlay that's visibly misaligned in some browsers, the player gets its own thin scrub strip, positioned entirely by this app (above the video, not overlapping native chrome at all), which both shows a floating preview frame above the pointer (YouTube-style) and can seek by click/drag via `videoEl.currentTime`. Native seeking is completely untouched — this is an additive, always-correctly-positioned companion control, not a replacement.

## Hardening and quality of life (Phase 5)

### Resume position — a separate table, deliberately not part of the index

Migration `0004_resume_positions.sql` adds a standalone `resume_positions(video_id, position_seconds, updated_at_unix)` table, keyed by the same opaque video ID, with **no foreign key to `videos`**. This is the one piece of Phase 5 schema that's user data, not disposable cache: the "SQLite is a disposable index/cache" invariant (see Invariants above) is about the *media index*, and a `DeleteStale`/full-reindex touching the `videos` table must never take resume positions down with it as a side effect. Keeping it in its own table with no cascade relationship makes that true by construction rather than by care — `TestResumePositionSurvivesReindex` in `internal/database/resume_test.go` asserts it directly (upsert a position, run the same `DeleteStale`-then-reinsert sequence a full reindex performs, confirm the position is still there).

The frontend (`Watch.svelte`) shows a dismissable "Resume from MM:SS?" banner rather than silently seeking — silent jumps are disorienting, per the assignment. A position is only offered if it's neither near the very start (`< 5s`, nothing to resume) nor within `8s` of the end (basically finished). Saving is throttled client-side to once per 10 seconds of playback progress (tracked via a plain, non-reactive `lastSavedAt` variable compared against `currentTime` on `timeupdate`, not a `setInterval` — ties the save cadence to actual playback progress rather than wall-clock time, so a paused video doesn't keep firing saves) plus a best-effort flush on `beforeunload` and on the route's `$effect` cleanup (in-app navigation away). `ended` clears the saved position outright, so a rewatch starts from the top.

### Filename search

`Store.SearchVideosByName` (`internal/database/search.go`) does a SQL `LIKE '%...%'` prefilter against `rel_path` (with SQLite's wildcard/escape characters escaped, reusing the same `escapeLike` the flattened view already needed), then a precise case-insensitive substring check against just `path.Base(relPath)` in Go — the SQL prefilter is a performance optimization for large libraries, but the actual "filename" semantics (not matching folder names elsewhere in the path) are enforced in Go, since portable SQLite has no basename function to lean on. Capped at 500 results (`searchResultCap`) as a defensive limit, not a documented paginated-search feature — search is deliberately meant to stay simple, not grow into a full-featured search engine. `GET /api/search?q=&root=` — `root` optional, spanning every configured root when omitted, returning each result's own `root` id alongside a `folderPath` the frontend reuses as the flattened view's "subfolder" secondary text (`Search.svelte` adapts a `SearchResult` into a `VideoEntry`-shaped object purely for this, since `VideoCard` doesn't need to know which root a result came from — the video ID alone is enough to watch it).

### Configurable ignored paths/extensions — one exclusion mechanism, reused everywhere for free

`EXTRA_HIDDEN_NAMES`, `EXCLUDED_PATHS`, `EXCLUDED_EXTENSIONS` (comma-separated env vars, parsed in `internal/config`) are applied once at startup via `filesystem.Configure(...)`, called from `main.go` right after `config.Load()`. This mirrors `hidden.go`'s existing package-level-map style for the built-in NAS/OS clutter list rather than threading a new parameter through every `Browse` call site — the process loads its config once, not per-request, so a package-level configurable set (not safe for concurrent reconfiguration, and not meant to be) is the simplest correct thing here.

The payoff of doing this inside `filesystem.Browse` itself, rather than as a separate filter layered on top: **every** consumer that already goes through `Browse` — the browse API, the indexer's own recursive walk (`internal/indexer` calls `filesystem.Browse` for traversal, per its existing design), and therefore the flattened view and filename search (both read from the index) — automatically respects the exclusion rules with zero additional code. An excluded folder is never even walked into by the indexer, so it's not just hidden from listings, it's never indexed at all. `EXCLUDED_PATHS` matches by prefix (`relPath == prefix || strings.HasPrefix(relPath, prefix+"/")`), applied to every entry's *own* relative path — so browsing directly into an excluded folder's URL also shows it empty, not just omitted from its parent's listing (unlike the hidden-name behavior, which only filters what a parent lists). This was a deliberate choice, not an oversight: "a raw footage folder you never want to see previews for" reads as wanting it gone everywhere, not just tucked out of the default view.

### Cache size limits and orphan cleanup (`internal/preview/cache.go`)

- **Orphans**: `Manager.CleanOrphans` computes the current valid content hash (`contentHash(id, size, mtimeUnix)`, the same function that names a video's cache files) for every row in `videos`, then removes any file in `cache/thumbs/`/`cache/sprites/` whose leading 32-hex-char hash isn't in that set. Runs two ways, per the assignment's "on scan completion? a separate endpoint? both?": automatically after every scan (`Indexer.AfterScan`, a callback field the indexer invokes post-scan without importing `preview` itself — wired in `main.go` — keeps the two packages decoupled), and manually via `POST /api/cache/clean-orphans`.
- **Size limit**: `CACHE_MAX_BYTES` (0/unset = unlimited) is enforced by `Manager.EnforceCacheLimit`, which evicts by **file modification time** (generation time), oldest first, down to 90% of the limit — a cushion so it doesn't immediately re-trigger. Generation time was chosen over access time deliberately: this app doesn't track per-file "last served" anywhere, and file *access* time (`atime`) is unreliable to lean on regardless — many Linux setups (including common Docker host mounts) run `noatime`, silently making atime-based LRU just decay to mtime-based behavior anyway, so mtime is both simpler and not actually giving anything up. Enforcement runs once at startup and via `POST /api/cache/enforce-limit` — not on every generation job's completion, which would mean an `os.ReadDir` size scan of the whole cache directory on every single thumbnail (wasteful on a hot path for no real benefit at homelab scale).
- **Manual rebuild**: `POST /api/previews/clear` wipes every cache file and resets every video's `thumb_status`/`sprite_status` to `pending` (`Store.ResetAllPreviewStatus`) in one call — regeneration then happens the normal lazy/pregenerate way, no separate "rebuild" code path. Per-video retry (`POST /api/videos/{id}/thumbnail/retry`, `.../sprite/retry`) just resets that one video's status, for forcing a retry on a permanently-failed file without waiting for it to change — surfaced as a toolbar-level "Rebuild previews" button in the frontend (`BrowseToolbar.svelte`, behind a native `confirm()`); per-video retry is backend-only for now, since the frontend doesn't currently surface per-video thumb/sprite status anywhere a retry button could attach to.

### Graceful FFmpeg shutdown — verified, not just assumed

No code change was needed here: `preview.Manager`'s FFmpeg calls already ran via `exec.CommandContext(m.baseCtx, ...)` (both `generate.go` and `sprite.go`), and `m.baseCtx` is the same `signal.NotifyContext`-derived context `main.go` cancels on `SIGINT`/`SIGTERM` — Go's `exec` package kills the child process automatically when its context is cancelled. This was verified empirically rather than taken on faith (per the assignment's explicit ask): a real sprite-generation job was started against an 8-minute test clip, confirmed running via `pgrep -f ffmpeg`, then the server process was sent `SIGTERM` directly — the ffmpeg child was gone within 300ms, no orphan surviving even after a further 2-second check. Repeated inside a real Docker container via `docker stop` (SIGTERM, not `kill -9`) with a job in flight: the container exited in ~0.2s (nowhere near the default 10s SIGKILL grace period), and the log showed the in-flight job's context-cancellation error logged cleanly on the way down.

### PWA manifest and icons

`web/public/manifest.json` plus `icon-192.png`/`icon-512.png`/`apple-touch-icon.png`, linked from `index.html`. No service worker — the app streams from the server and is useless offline, so an installable-without-offline-support manifest is the whole scope, per the assignment. The three PNGs were generated from scratch to exactly match `favicon.svg`'s design (dark rounded square, light play-triangle) with a small throwaway Go program (`image`/`image/png` from the standard library: rounded-rect and triangle point-membership tests, rasterized per-pixel) rather than an SVG-to-PNG converter, since neither `rsvg-convert`/`ImageMagick`/`Inkscape` nor a Python `cairosvg`/Pillow install was available in the environment this was built in — worth noting here in case a real design tool becomes available later and these should be regenerated properly instead.

## Container remux (Phase 6)

### The design problem this resolves: seeking during a live remux

The original plan for this phase flagged "seeking during a live remux needs design work first" as an open question — MKV/AVI/TS files with browser-compatible codecs (H.264/HEVC video, AAC/MP3 audio) just sitting in a container browsers won't direct-play. The concern was real: if remuxing happened on-the-fly while streaming, a seek to an arbitrary byte offset would either require re-starting the remux from scratch (breaking seeking) or a much more complex fragmented/segmented streaming scheme.

This was resolved empirically, not by designing around live remuxing: `ffmpeg -c copy` (repackaging streams into a different container with no decode/encode work) is fast enough — measured at ~1.4s for a 21-minute, 669 MB real-world `.ts` file, and confirmed again during Phase 6 acceptance testing (a full Docker end-to-end request against the same file completed, including the remux, in well under a second) — to simply **generate and cache the whole remux before serving anything**, the same "generate once, cache on disk, serve statically" model already used for thumbnails and sprites. Once the cached file exists, it's served through the exact same `http.ServeContent`-based Range-request path every other video uses — no special-cased seeking logic anywhere. This was verified directly against the real `.ts` file: seeking to an arbitrary point mid-file and resuming playback worked correctly against the cached remux, both via raw `curl -H "Range: ..."` requests and via real `<video>` playback in a browser tab.

### Eligibility (`internal/preview/remux.go`)

`NeedsRemux(name, videoCodec, audioCodec)` combines two independent checks:

- **Container**, by file extension (`.mkv`, `.avi`, `.ts`) — not ffprobe's `format_name`, which is ambiguous for this purpose (it reports both `.mkv` and `.webm` as `"matroska,webm"`, so it can't distinguish a file that needs remuxing from one that's already fine).
- **Codec**, against a small allow-list (video: `h264`, `hevc`; audio: `aac`, `mp3`) — the same codecs a `-c copy` remux into MP4 can actually carry and a browser can decode. A file whose codec isn't on this list (e.g. `mpeg2video`, common on older TV-tuner recordings) is a codec problem, not a container problem — remuxing wouldn't make it playable, and this app never transcodes (invariant 3).

Real-world validation: the `.ts` file used throughout this phase's testing turned out to carry a `timed_id3` metadata stream alongside its video/audio — a stream MP4 can't hold. The remux command maps only the first video and first audio stream explicitly (`-map 0:v:0 -map 0:a:0`) rather than a blanket `-c copy`, specifically because a blanket copy failed the mux entirely on this file. Nearly all of the user's real files at time of writing are in this same shape (H.264/AAC inside MPEG-TS), which is what motivated writing this phase's remux command against a real problem file rather than only synthetic test fixtures.

### Schema and generation

Migration `0005_remux.sql` adds `remux_status`/`remux_error`, mirroring `thumb_status`/`thumb_error` exactly: same `pending`/`ok`/`error` states, same minimal-row upsert (`SetRemuxOK`/`SetRemuxError`) so generation doesn't require the indexer to have run first, same reset-to-`pending` on `UpsertOK`/`UpsertError` when a file's `size`/`mtime` change. (This reset was initially missed for `remux_status` specifically — added alongside `thumb_status`/`sprite_status` in both upserts after a test written against the established thumbnail-lifecycle pattern caught the gap: without it, a changed file's stale `"ok"` status would make `FilterNeedingRemux`/`ListPendingRemux` skip it for background/pregenerate regeneration, even though the content-hash-named cache path for the new content wouldn't exist yet. On-demand generation via `RequestRemux` — the path an actual `/stream` request takes — was unaffected either way, since it checks the cache file directly rather than trusting the stored status for anything but a fast "already failed" short-circuit.)

Output is written to `DATA_DIR/cache/remux/<hash>.remux.mp4`, same content-hash naming (`sha256(videoID|size|mtimeUnix)`) as thumbnails/sprites, via a temp-file-then-rename so a concurrent reader never sees a partial file. Remux jobs share the same `preview.Manager` and worker-pool semaphore as thumbnails/sprites (a third `ensureJob` key prefix, `"remux:<id>"`) — deliberately, for the same reason thumbnails and sprites already share one pool: independent pools per asset type would let total FFmpeg concurrency exceed the configured bound.

### Serving

`GET /api/videos/{id}/stream` (`handleStream`) checks `NeedsRemux` against the video's indexed codec metadata; if eligible, it calls `RequestRemux(..., wait=true)` (same bounded-wait-then-503 pattern as thumbnail/sprite requests) and serves the cached MP4 instead of the original file — via `streaming.ServeFile` with a name whose extension is rewritten to `.mp4` (not the original `.ts`/`.mkv`/`.avi` name), since `ServeFile` derives `Content-Type` from that name and the bytes being sent are now actually MP4, not the source container. A file that's remux-eligible but whose remux attempt failed returns `422` with a clear message rather than silently falling through to serve the original (unplayable) bytes. A non-eligible file's request never enters this branch at all — verified with a regression test asserting byte-for-byte-identical behavior to the pre-Phase-6 stream path.

### Frontend

`videoEntryDTO`/`metadataFields` (`internal/api/dto.go`) gain `remuxEligible` (omitted when false, via `NeedsRemux` once codec metadata is known). `web/src/lib/codec.ts`'s `isLikelyIncompatible` checks this first and returns `false` (compatible) immediately when set, regardless of what `canPlayType()` would say about the file's original container/codec strings — those strings describe bytes the browser will never actually receive, since the file is served as a remux. `.ts` was also added to `MIME_BY_EXT` (`video/mp2t`) for consistency with the backend's extension map, so a `.ts` file that *isn't* remux-eligible (an incompatible codec, e.g. `mpeg2video`) still gets a confident, correct "may not play" badge instead of the "unknown extension, no confident answer" fallback.

## Onboarding, settings, and an access gate (Phase 7)

### Root auto-discovery — mount boundaries, not every subdirectory

`MEDIA_ROOT` changed meaning: it's now the *parent* directory of your media, not necessarily a single root's own path. The first implementation auto-discovered a root for *every* immediate subdirectory unconditionally — this was wrong for the common deployment shape (one Docker volume, `-v host:/media`, containing organizational subfolders like `Anime/`, `Misc/`, `TV/`): it fragmented one library into several disconnected ones with their own root switcher, breaking unified browsing/search across content that was never meant to be separate. Caught from real usage against a real single-mount deployment, not in review.

`config.DiscoverRoots(parentDir)` (`internal/config/mount.go`) instead distinguishes a **genuinely separate mount** from a **plain subfolder** using the filesystem device ID (`stat`'s `st_dev`, the same signal `findmnt`/`mountpoint` rely on): a directory bind-mounted from a distinct host path (`-v host1:/media/Movies -v host2:/media/TV`) reports a different device than `parentDir` itself, while an ordinary subfolder within one mount reports the same one. Only a distinct-device subdirectory is "promoted" into its own root (ID and default display name equal to the folder's own name); everything else — plain subfolders, loose files directly in `parentDir`, and (if device detection isn't available at all, e.g. an unsupported platform) *every* subdirectory — stays together as a single synthetic `"main"` root, `parentDir` itself, browsed as one folder tree exactly like Phases 1-6. `"main"` is only created when there's something left for it to show; if every subdirectory was promoted and there are no loose files, it's omitted entirely. `deviceID` is indirected through a package variable (`deviceIDFunc`) so tests can simulate a genuinely separate mount — real device separation can't be produced in a unit test without OS-level mount privileges — and a matching `config.SetDeviceIDFuncForTesting` export lets `internal/api`'s integration tests do the same across the package boundary.

Because `"main"`'s own `Path` is `parentDir`, and `parentDir` still filesystem-wise contains any promoted subdirectories, `config.Root` gained a `HiddenChildren []string` field — the promoted roots' names — and `filesystem.Browse` gained a variadic `hiddenTopLevel` parameter (almost every caller passes none) that excludes those exact names, but only at the root's own top level, never deeper (a promoted mount's name could coincidentally match an unrelated folder several levels into `"main"`'s tree, which must still show normally). Without this, a promoted subdirectory's files would be reachable under two different video IDs — once via its own root, once via browsing into it from `"main"` — with independent index rows, thumbnails, and resume positions for the same underlying file.

`settings.MergeRoots` then layers persisted per-root overrides (`displayName`, `hidden`) on top of whatever `DiscoverRoots` produced — a hidden root is dropped entirely, a display-name override replaces the folder-name default, and a root with no override at all passes through unchanged. This two-step split (pure filesystem discovery, then a separate merge with settings) keeps `internal/config` from needing to know anything about `internal/settings`, avoiding an import cycle and keeping root *discovery* logic testable independent of settings storage.

An empty same-device subdirectory never counts toward "main has content" (a cheap shallow `Readdirnames(1)` check, `dirHasEntries`) — caught immediately when actually deploying two separately-mounted volumes at `-v host1:/media/videos -v host2:/media/videos2`: Alpine's base image (this app's own runtime image) ships pre-existing empty `/media/cdrom`, `/media/floppy`, `/media/usb` directories (a standard FHS removable-media convention), and `/media` is exactly the path this project's own docs recommend mounting at. Without this check, those three empty, irrelevant directories would earn a spurious third "main" library alongside the two real ones, on literally every deployment that follows the documented setup.

Because a newly mounted drive must appear without a container restart (acceptance criterion), the discovered-and-merged root list isn't fixed at startup: `api.Server.refreshRoots()` re-discovers and re-merges on demand, then pushes the result into three places that each used to take a fixed `[]config.Root` only at construction — the server's own root map, `indexer.Indexer` (`SetRoots`), and `preview.Manager` (`SetRoots`) — each now guarded by its own mutex (`Server.rootsMu`, reusing `Indexer.mu`, and a new `Manager.rootsMu` kept separate from the existing job-bookkeeping `Manager.mu` since root updates are logically unrelated to and far less frequent than job dispatch). `refreshRoots` is called at startup, after setup, after a settings update, and from the settings-page rescan action.

`Server.allRoots()` returns roots in *discovery order* (an explicit `rootsOrdered` slice kept alongside the lookup map), not map-iteration order — Go randomizes map iteration per-process, which briefly made the frontend's home-redirect target and root-switcher order change on every single page load for no reason before a test (`TestConfigRootsOrderIsStable`) caught it.

### Settings storage: `DATA_DIR/config.json` (`internal/settings`)

A small mutex-guarded `Store`: `Load` (no-op, not an error, if the file doesn't exist yet — "not configured" is a real, expected first-run state) and `Save` (atomic: write to a `.tmp-<pid>` file in the same directory, then rename, mirroring the pattern `internal/preview`'s cache writers already use, so a crash mid-write can never leave a half-written `config.json` — verified with a concurrent Save/Get race test under `go test -race`). Shape:

```json
{
  "serverName": "My Homelab",
  "authUsername": "admin",
  "authPasswordHash": "$2a$...",
  "sessionSecret": "<base64, random 32 bytes>",
  "roots": { "anime": { "displayName": "Anime", "hidden": false } }
}
```

Deliberately not part of `index.db` (invariant 5): deleting the disposable index to force a rescan must never also erase login/server setup — verified directly, both by a unit test and by a real Docker acceptance run (delete `index.db*`, restart, still requires login with the same credentials, roots intact).

### Password hashing and sessions (`internal/auth`)

- **Passwords**: bcrypt (`golang.org/x/crypto/bcrypt`) — the one new external dependency this phase adds, justified the same way `modernc.org/sqlite` is (this project prefers a small dependency surface, but doesn't avoid one entirely when there's no reasonable stdlib alternative): there's no stdlib password hash, and `x/crypto` is as close to "stdlib-blessed" as Go gets for this.
- **Sessions**: no server-side session table, a deliberate choice — a session is a token of `base64url(expiry-unix-as-8-bytes) + "." + base64url(HMAC-SHA256(expiry-bytes, sessionSecret))`. Verifying just means recomputing the HMAC (`hmac.Equal`, constant-time) and checking the decoded expiry against `time.Now()`. Rotating `sessionSecret` (on a password change) invalidates every outstanding token at once — the simplest correct way to force a global re-login with no revocation list to maintain, at the cost of not being able to invalidate *one* session without invalidating all of them. Acceptable for this app's threat model (a household's shared Tailscale network, not a multi-tenant system).
- **Session lifetime: 90 days** (`auth.SessionLifetime`). Chosen deliberately long, per the assignment's explicit guidance: this gates casual access on a trusted home network, not a high-security system, and frequent re-logins would be pure friction with no real security benefit — the actual security boundary is still Tailscale/private-LAN (§5), not this cookie.
- **Cookie**: `HttpOnly`, `SameSite=Lax`, and deliberately **no `Secure` flag** — many people reach this app over plain HTTP directly on their tailnet (not through `tailscale serve`), and Tailscale already encrypts the transport at the WireGuard layer; requiring `Secure` would silently break login for anyone not proxying through `tailscale serve`. Cookie-based auth was chosen specifically (over e.g. a bearer token) because it covers the `<video src>` streaming endpoint for free — the browser attaches cookies to a plain media-element request automatically, with no custom-header plumbing needed for something that isn't `fetch`.

### Auth middleware and what stays public

`Server.requireAuth` wraps a handler so it 401s (stable JSON error shape) unless the request carries a valid, unexpired session cookie; "not configured yet" fails the same way "invalid session" does (no secret exists to verify against, so every protected route is unreachable pre-setup by construction, not by a separate check). Every route is wrapped explicitly at registration in `server.go`, rather than via a path-prefix gate, so nothing is protected by accident or omission — the exceptions are enumerated, not inferred:

- `GET /api/config`, `POST /api/setup`, `POST /api/auth/login`, and static asset serving (`/`) — the SPA shell must always be able to load and figure out which of onboarding/login/the-app to render, regardless of auth state.
- `GET /api/health` — also public, and deliberately so, even though every other route is now gated: Docker's own `HEALTHCHECK` (`wget`, no cookie jar) and any external monitoring have no way to authenticate, and health leaks nothing beyond what it already did (root IDs and reachability). This was initially wrapped in `requireAuth` along with everything else during development, which would have made the container report unhealthy forever — caught by a regression test (`TestHealthStaysPublic`) before it shipped, not by observing a real container fail.

### Frontend

`session.svelte.ts` is a small reactive store (same hand-written-class pattern as `router.svelte.ts`) fetching `GET /api/config` on load and exposing `{loading, configured, authenticated, serverName, roots}`. `App.svelte`'s top-level render is gated on exactly those three states — not configured → `Onboarding.svelte`, configured-but-not-authenticated → `Login.svelte`, both → the normal app (`TopBar` + router-driven routes, now including `Settings.svelte`) — independent of whatever URL was actually requested, so a deep link survives login/onboarding (the router's own state is untouched; only the top-level gate changes what's rendered around it).

`api/client.ts`'s `onUnauthorized` callback fires on *any* 401 from *any* endpoint, not just the ones the session store itself calls — a session that expires mid-browse gets the user back to the login screen on its very next API call, rather than surfacing a raw "unauthorized" error in whatever component happened to be fetching at the time.

## Tags and Recently Added (UI refresh, unplanned/ad hoc — not a numbered phase)

Requested directly by the user after Phase 7 shipped, alongside a visual restyle toward a mockup — not part of the original phased roadmap, built on a separate branch (`feature/ui-refresh`) specifically so the working Phase 1–7 state on `main` stayed protected.

### Tags: global, freeform, many-to-many, deliberately not part of the disposable index

Migration `0007_tags.sql` adds `tags(id, name UNIQUE COLLATE NOCASE, color, created_at_unix)` and a join table `video_tags(video_id, tag_id REFERENCES tags(id) ON DELETE CASCADE, tagged_at_unix)`. `video_tags.video_id` deliberately has **no foreign key to `videos`** — the same reasoning as Phase 5's `resume_positions` table (see above): tags are user data, not part of the disposable media index, so a `DeleteStale`/reindex must never silently drop them. `video_tags.tag_id`'s cascade to `tags` is safe regardless, since `tags.id` is a stable, independently-managed identifier.

Tag creation is freeform and ad hoc (typed while tagging a video, no separate management screen) and global (one tag list across every root/library, not per-library) — both explicit user decisions. `Store.CreateOrGetTag` does `INSERT ... ON CONFLICT(name) DO NOTHING` followed by a `SELECT ... COLLATE NOCASE`, so retagging with a name that differs only in case reuses the existing tag rather than erroring or creating a near-duplicate — enforced at the schema level (`UNIQUE COLLATE NOCASE`), not just in application code. Colors are assigned deterministically (FNV-1a hash of the lowercased name, modulo a fixed 10-color palette in `internal/database/tags.go`) rather than stored per-tag-creation or picked via a color UI — a tag that's deleted and recreated with the same name gets the same color back, and there's no color-picker control to build or maintain.

Filtering by tag uses **OR semantics** (match any selected tag) — another explicit user decision — and is done **in Go, not SQL**: `handleBrowse`/`handleSearch`/`handleRecent` already batch-fetch each listed video's tags via `Store.GetTagsForVideos` purely to *display* them on cards, so `filterByAnyTag` (`internal/api/handlers.go`) reuses that same already-fetched map rather than issuing a second, separate SQL query for filtering. A `Store.FilterByAnyTag` SQL method was written and then deliberately removed for this reason — it would have been a redundant round-trip, not a simplification.

Bulk tagging (`POST /api/tags/bulk`, `Store.TagVideos`) applies one tag to many videos transactionally; per the assignment, video IDs in the bulk payload are applied best-effort (not individually validated through the normal `resolveVideoID` path) since a bulk operation shouldn't fail entirely because one of many selected videos disappeared from disk between selection and submission.

### Recently Added: an immutable "first seen" timestamp, not the mutable "last reindexed" one

`indexed_at_unix` (Phase 2) already exists but gets overwritten on every reindex of a changed file — using it for "recently added" would make a video jump back to the top of the list just because its size or mtime happened to change, which isn't what "added" means. Migration `0006_first_indexed.sql` adds a separate `first_indexed_at_unix`, set once: every one of the 8 row-creating upsert paths (`UpsertOK`/`UpsertError` for the indexer, `SetThumbOK`/`SetThumbError`/`SetSpriteOK`/`SetSpriteError`/`SetRemuxOK`/`SetRemuxError` for the "minimal row" pattern those Phase 3/4/6 features already use when they see a file before the indexer does) includes it in the `INSERT` values, but **none of them** include it in their `ON CONFLICT DO UPDATE SET` clause — so whichever subsystem's upsert happens to create a video's row first sets the timestamp, and every later upsert from any subsystem leaves it untouched, by construction rather than by an extra "is this already set?" check.

`Store.ListRecentlyAdded` (`internal/database/recent.go`) queries `first_indexed_at_unix > 0 ORDER BY first_indexed_at_unix DESC`, spanning all roots by default (`GET /api/recent?root=` optional, same pattern as filename search). The DTO gate for the API's `addedAt` field is intentionally different from the other probe-derived metadata fields (`duration`, `width`, etc.): those require `status == "ok"` (an actual successful `ffprobe`), but `addedAt` only requires the row to exist at all — a file that's indexed but whose `ffprobe` failed still has a real "first seen" moment worth showing.

### Frontend restyle

Warm amber/stone palette (`app.css`) replacing the previous cool gray/blue theme, and a mockup-inspired layout pass: folders render as a separate, visually distinct row of wide cards above the video grid (`BrowseGrid.svelte`) instead of same-sized tiles mixed in with videos; the folder-tree toggle moved from a labeled button in the toolbar to an icon button in the persistent top bar (`TopBar.svelte`); a "Recently Added" nav link and a tag-filter pill row (`TagFilterBar.svelte`) were added alongside the existing search/sort/view controls. None of this is a literal copy of the reference mockup's colors or exact spacing — the user was explicit that "you don't have to mirror everything," only that the general visual direction and the two functional changes (tags, recently-added) land. Favoriting/a "show favorites" view, also present in the mockup, was explicitly deprioritized and not built.

**`TagPicker`'s popover alignment (`align: 'start' | 'end'` prop) is a mobile-driven fix, not a cosmetic option.** The popover is `position: absolute` relative to its trigger button, and originally always right-aligned (`right: 0`) — correct when the trigger sits at a container's top-right corner (`VideoCard`'s tag button), since the popover then extends leftward *into* the (usually-wide) card. But `Watch.svelte`'s "+ Tag" button and `Browse.svelte`'s bulk "Tag selected…" button both sit near the *left* edge of their row, where right-aligning a fixed 200px-wide popover pushed it up to ~65px off the left edge of a 375px-wide phone viewport — confirmed via `getBoundingClientRect()` during a real mobile-viewport check (this app has no automated visual-regression coverage; this class of bug is only caught by actually opening the popover at phone width, not by `svelte-check`/`go vet`/unit tests). Fixed by adding `align="start"` at those two call sites, which switches the popover to `left: 0`, and adding `max-width: calc(100vw - 32px)` as a backstop against the same failure mode on an even narrower screen. `TopBar.svelte`'s brand text and root-switcher were also changed from a fixed/`flex-shrink: 0` width to shrink-with-ellipsis, after the same mobile check found a long server name and the search box competing for space on a phone-width top bar could squeeze the search input down to an unusably narrow sliver.

### Second UI-refresh pass: four real bugs, plus a closer pass at the mockup's nav shell

The first UI-refresh pass above shipped with several bugs invisible to `go test`/`svelte-check`/`npm run build`, only found once the user actually used it — a concrete demonstration of why this project treats "verified in a browser" as a separate, required step from "compiles cleanly."

- **A video card's thumbnail didn't open the video — only the filename text did.** Root cause: `ScrubPreview.svelte`'s hover/touch-scrub overlay (`.scrub-layer`, `z-index: 2`, covering the whole thumbnail) painted *above* the card's whole-card navigation link (`.card-link`, `z-index: 1`), silently swallowing every click over the thumbnail — the link only remained reachable over the filename/metadata area below the thumbnail, which `.scrub-layer` doesn't cover. Fixed by giving `ScrubPreview` its own `onActivate` callback and having it perform navigation (or, in select mode, toggle selection) itself on a plain click/tap, rather than relying on a click "falling through" to a sibling element it happens to be layered above — DOM click events don't fall through to siblings, they target whatever's topmost, so the topmost element has to own the behavior. `VideoCard.svelte`/`VideoRow.svelte` pass `onActivate={selectable ? () => onToggleSelect?.(video.id) : () => router.navigate(watchPath(video.id))}`.
- **Grid view rendered at the same card size as Large view, and both could force horizontal scrolling.** Root cause: `BrowseGrid.svelte`'s `.grid`/`.grid.large` used plain `repeat(N, 1fr)` column tracks. A CSS Grid track's *automatic minimum width* defaults to its content's min-content size unless overridden — for a `white-space: nowrap; text-overflow: ellipsis` filename, min-content is the filename's full unwrapped width, which can exceed the track's fair-share `1fr`, inflating every track (and the whole grid) past the viewport. This is a well-known "grid blowout" failure mode; the fix is `repeat(N, minmax(0, 1fr))`, which the original reference mockup this session worked from already used for exactly this reason — missed when translating it into this app's components the first time. Verified by injecting an intentionally extreme (140-character) filename and confirming `document.body.scrollWidth` stayed equal to `window.innerWidth` across grid/large view at both mobile and desktop widths.
- **Bulk-tagging a multi-video selection didn't return to normal browsing** — the picker and "N selected" bar stayed up after a tag was successfully applied, requiring an explicit "Cancel" to see the result. `TagPicker.svelte`'s `applyTag` now calls `onClose()` immediately after a *bulk* apply succeeds (single-video tagging is left alone — that picker is meant for adding/removing several tags in one sitting, not a one-shot action). `Browse.svelte` passes a dedicated `exitSelecting` (not the existing `toggleSelecting`, which flips rather than unconditionally exits) as that `onClose`, so closing the picker and leaving select mode happen together.
- **The top bar didn't meaningfully change from the first UI-refresh pass**, per direct user feedback after trying it, alongside a fuller HTML/CSS mockup of the intended nav shell. This prompted a real structural change, not another visual-only pass: a new persistent, collapsible `Sidebar.svelte` (brand, "All Videos"/"Recently Added" nav — this is "the left expanding menu" the user meant Recently Added should live in — the folder tree, and Settings) rendered app-wide in `App.svelte` alongside a slimmed-down `TopBar.svelte` (sidebar-toggle icon, a right-aligned fixed-width search box, and — only on the Browse route, read directly from `router.route` rather than prop-drilled — icon-only Grid/List/Large buttons and a sort pill, both moved out of `BrowseToolbar.svelte`). `FolderTree.svelte` was stripped down to just its tree-rendering logic (no more backdrop/drawer chrome of its own), since `Sidebar` now owns the responsive drawer/backdrop behavior at the top level; a click anywhere on an `<a>` inside `Sidebar` is caught by one delegated handler on the `<aside>` itself (`onSidebarClick`) rather than by passing an `onclick` prop to each individual `Link.svelte`, which would silently replace `Link`'s own SPA-navigation handler (see `Link.svelte`'s prop-forwarding hazard, noted elsewhere in this file). The sidebar defaults open on desktop but closed on a first mobile visit (`preferences.svelte.ts`'s `defaultShowSidebar()`, gated on `matchMedia('(max-width: 899px)')` and only used when no preference has ever been saved) — defaulting it open on phone width would otherwise cover the entire screen with a slide-over drawer on first load.

### Third UI-refresh pass: Recently Added had drifted from Browse, plus color variety

- **Recently Added had no Grid/List/Large view options and reintroduced the exact same horizontal-overflow bug already fixed in Browse.** Root cause: `Recent.svelte` never actually used `BrowseGrid.svelte` — it had its own copy-pasted `.grid` with the same un-fixed plain `repeat(N, 1fr)` columns (predating the `minmax(0, 1fr)` fix above, since that fix only touched `BrowseGrid.svelte`), and no view-mode UI of its own. Fixed by making `Recent.svelte` a genuine consumer of `BrowseGrid`/`BrowseList` (passing `folders={[]}`, since Recently Added spans every root and has no folder concept) instead of a parallel, drifting implementation — the same bug class as the first UI-refresh pass's lesson: one shared component fixed once beats two copies that silently diverge. This needed the `recent` route to carry its own `view` (and keep `tagIds`) in its query string, mirroring Browse's `BrowseQuery` (`router.svelte.ts`'s `Route` type: `{name:'recent'} & Pick<BrowseQuery,'view'|'tagIds'>`), and `TopBar.svelte`'s view-mode buttons to target either route shape (`setView` branches on `router.route.name`; sort stays Browse-only, via a separate `hasSort` gate, since "recently added" has no other sort order to offer). `recentPath()` gained a `{view?, tagIds?}` param, persisting the view choice through the same `VIEW_STORAGE_KEY` Browse already uses (a new `persistView` — writes just that one key, unlike `persistViewSort` which also needs a sort value Recently Added doesn't have) so switching to grid on one and back to the other keeps it.
- **More color variety, not just the single amber accent, per direct request** ("orange as a main accent color is fine but more colors would make this livelier"), using subfolders as the concrete example given. `lib/folderColor.ts` assigns each folder a color deterministically from its name (FNV-1a hash modulo a fixed 10-color palette) — the same technique, and literally the same palette values, as the backend's per-tag color assignment (`internal/database/tags.go`'s `colorForTagName`/`tagPalette`), so the app's color language stays consistent between tags and folders rather than introducing an unrelated second scheme. Applied to `FolderCard.svelte` (grid/large folder tiles) and `FolderRow.svelte` (list view); deliberately *not* applied to the sidebar's `FolderTree`/`FolderTreeNode` (kept single-color, matching the reference mockup's own sidebar tree) — a dense nested list is exactly where many simultaneous colors stop reading as "lively" and start reading as noise, whereas a handful of same-level folder tiles/rows is the case the user actually asked about. The accent color itself is untouched on state-indicating UI (active nav link, selected view-mode button, selected checkmark) — that's a functional "this is the current selection" signal, not decoration, and making a selection indicator multi-colored would undermine what it's for rather than make the app livelier.

## Reliability fix: stuck failures and unbounded generation time (unplanned, not a numbered phase)

A separate Claude Code session had made two uncommitted changes to `cmd/server/main.go`/`internal/preview/generate.go` attempting to fix "thumbnail/sprite production became extremely slow" on a large library: triggering `Pregenerate` automatically after every scan, and removing the `nice -n 15` CPU-priority throttling entirely. Reviewed before either was committed. The auto-pregenerate idea was kept (see below); removing `nice` was reverted — it directly contradicts this project's Phase 3 requirement that generation run "at low CPU priority" so it "doesn't compete with an actively streaming video," and address the wrong problem: the user's own description (fine, then a cliff-edge to ~30 minutes per thumbnail, with nothing else running) doesn't match gradual CPU-contention degradation at all.

**Root cause: no per-job timeout anywhere in the generation pipeline.** Every job (`runThumbJob`/`runSpriteJob`/`runRemuxJob` in `internal/preview/manager.go`) ran its FFmpeg subprocess under `m.baseCtx` — the server's whole-lifetime context, which only ever cancels on shutdown. A single stalled FFmpeg invocation (a pathological file, a storage stall) could hold one of the worker pool's 2 slots indefinitely, with nothing to intervene. Sprite generation makes this much more likely to surface: up to ~150 sequential single-frame extractions per video (see "Preview sprites" above), so one bad frame partway through a sprite job drags out the whole job with no way to bound it. With only 2 workers total, even one stuck job backs up everything queued behind it — which reads as "generation became extremely slow" even though most individual jobs are still fine, and explains the cliff-edge (fine until the one problem file is hit) far better than a scheduling-priority story would.

**Fix**: each job now runs under its own `context.WithTimeout(m.baseCtx, ...)`, sized generously so a slow-but-fine large file is never wrongly killed — `thumbnailJobTimeout` 5 minutes (one extraction, or two counting `GenerateWithFallback`'s retry), `spriteJobTimeout` 20 minutes (~150 sequential extractions plus assembly), `remuxJobTimeout` 30 minutes (`-c copy`, no decode work, but still proportional to a very large file's I/O). A killed job fails through the exact same `SetThumbError`/`SetSpriteError`/`SetRemuxError` path any other failure already used — no new failure handling needed, just a bound on how long a job is allowed to occupy a worker slot before it's forced into that path. These are `var`, not `const`, specifically so `TestJobTimeoutKillsHungGeneration` can override `thumbnailJobTimeout` to a couple of milliseconds via an exported `SetThumbnailJobTimeoutForTesting` (same test-seam pattern as `internal/config`'s `SetDeviceIDFuncForTesting`) rather than a test actually waiting out a multi-minute timeout — FFmpeg's own process-spawn overhead alone reliably exceeds a 1ms budget, so the test is deterministic, not a timing race.

**Also added, per direct request: bounded automatic retry for failures**, since the user had hit this exact class of problem for real — a UID mismatch between the container and an external drive during deployment failed the first couple hundred thumbnails, which then stayed in `error` status forever (this project's established design was deliberately "permanent failure isn't retried until the file changes or an explicit manual retry" — reasonable for a genuinely broken file, wrong for a whole batch failed by something environmental that gets fixed later). Migration `0008_retry_counts.sql` adds `thumb_retry_count`/`sprite_retry_count`/`remux_retry_count`, mirroring the existing parallel-columns pattern. `Store.RequeueRetryable{Thumbnails,Sprites,Remux}(ctx, maxRetries)` resets qualifying `error` rows (`retry_count < maxRetries`) back to `pending` and increments the counter in one `UPDATE`; `Manager.RequeueFailedForRetry` calls all three and is wired into `cmd/server/main.go`'s existing `AfterScan` hook, right before the (kept) auto-`Pregenerate`/`PregenerateSprites` calls — so a batch of environmental failures self-heals on the next scan (in practice, often just the next container restart) with zero manual per-video clicks. `maxAutoRetries` is 3: a genuinely broken file (verified against the user's real library — a single real stuck failure turned out to be an audio-only `.mp4` with no video stream at all, which can never succeed) gets three automatic attempts and then is left alone rather than retried forever, still fixable with the pre-existing manual per-video retry endpoint. Every place that already reset status to `pending` for other reasons (`UpsertOK`/`UpsertError` on file change, `Reset{Thumb,Sprite,Remux}Status`'s manual retry, `ResetAllPreviewStatus`'s full rebuild) now also resets the matching retry counter to 0 — a changed file or an explicit retry both deserve a fresh budget, not to inherit a cap already hit by the file's previous content/attempt history.

Verified end-to-end against a real permission failure, not just unit tests: made `DATA_DIR/cache/thumbs` read-only before starting a test server against two real clips (both correctly failed and recorded as `error`), fixed the permission, triggered `POST /api/scan`, and confirmed via server logs (`post-scan retry requeue count=2`) and `GET /api/thumbnails/status`/`.../sprites/status` (both `{"ready":2,"errored":0}` afterward) that both fully recovered with no manual intervention.

## Player controls don't auto-hide in fullscreen (mobile)

`PlayerControls`/`TimelineScrubber` were always-visible flex children of `.player`, with no inactivity handling at all — fine in windowed playback (they sit below the video, never obstructing it), but in fullscreen (the Fullscreen API path — `playerEl.requestFullscreen()`, used everywhere except iOS, which takes the native-`<video>`-fullscreen branch instead and gets Apple's own auto-hiding chrome for free) they just stayed on screen permanently, on top of the video, with nothing to make them go away.

Fixed in `Watch.svelte`: both are now wrapped in a `.bottom-controls` container. Windowed styling is untouched (a normal flex child, always visible). Only `.player:fullscreen .bottom-controls` becomes an absolutely-positioned overlay pinned to the bottom, on a `linear-gradient` scrim for legibility over bright video content. A small inactivity state machine (`controlsVisible`, a 3s `setTimeout` armed by `pointermove`/`touchstart` on `.player`) adds/removes a `.hidden` class that fades it out via opacity/visibility (not `display:none`, which would cut the transition short) and drops `pointer-events` so a tap reaches the video underneath instead of an invisible-but-still-there control. Auto-hide is deliberately gated on `isFullscreen && !paused` — paused always keeps controls visible (so there's always an obvious way to resume), and leaving fullscreen unconditionally resets `controlsVisible = true` in the `fullscreenchange` handler, so returning to windowed playback never leaves anything stuck invisible. A `.hide-cursor` class on `.player`, driven by the same state, hides the mouse cursor too (a cheap desktop-fullscreen bonus from the same mechanism).

Verified by mocking `document.fullscreenElement` (via `Object.defineProperty`) and dispatching a synthetic `fullscreenchange` event, rather than the real Fullscreen API — browser-automation-driven clicks don't count as the "genuine user gesture" `requestFullscreen()` requires, and the sandboxed browser pane used for this session's verification blocks it outright (`Permissions check failed`). This exercises everything except the real `:fullscreen` CSS pseudo-class match itself (a standard, low-risk selector) — confirmed: hides after 3s idle while playing, reappears and reschedules on activity (repeatedly, not just once), immediately reappears and stays visible on pause (including a video reaching its natural end mid-test), and resets on a simulated fullscreen exit.

## Decisions and deviations

- **`root` added to `GET /api/videos/{id}`.** The Phase 1 spec's field list for this endpoint didn't include it, but the player page needs to link back to the containing folder (`/browse/:root/*path`), and the video ID itself is an opaque token to the frontend (decoding it is a backend-only concern). Adding `root` is additive and doesn't change any other documented field.
- **Frontend embed placeholder.** `web/dist/.gitkeep` is the only frontend build artifact committed to git — `web/dist/*` is otherwise gitignored. This exists solely so `//go:embed all:dist` in `web/embed.go` has something to embed for plain `go build`/`go vet`/`go test` without requiring the frontend to be built first. The real build output is produced by `npm run build` (locally) or the frontend stage of the `Dockerfile`. If `index.html` isn't present in the embedded FS, the server serves a clear "frontend not built" error instead of crashing.
- **Go 1.27 / Node 22.** Pinned to the versions available in the development environment at the time of Phase 1 (`go.mod` sets `go 1.27.1`; `Dockerfile` uses `golang:1.27-alpine` and `node:22-alpine`). Bump deliberately, not incidentally.
- **Final Docker image is `alpine`, not `distroless`.** Distroless has no shell, which makes the `HEALTHCHECK` (which needs `wget`) awkward. Alpine keeps the image reasonably small while keeping the healthcheck simple; a non-root user is created explicitly since alpine doesn't ship one by default. Phase 2 adds `apk add ffmpeg` (~118 MB) to this stage for `ffprobe`; the image is no longer minimal-static, but staying on alpine (rather than switching approach) keeps the healthcheck and package install simple.
- **Migration runner is hand-rolled, not a library.** `golang-migrate` or similar would work, but the app only ever needs forward-only, embedded-file migrations — a ~70-line runner (`internal/database/migrate.go`) covers it without a new dependency, consistent with this project's preference for a small dependency surface.
- **`SetMaxOpenConns(1)` on the SQLite connection.** See "Index and metadata" above. A single-writer, single-reader-at-a-time model is the simplest correct thing for this app's scale; WAL mode is still enabled so it's a deliberate choice, not an oversight, if this needs to change later.
- **Indexer reuses `filesystem.Browse` for traversal** rather than a separate `filepath.WalkDir`. Slightly less efficient (each folder's listing is sorted and breadcrumbed for no reason during a scan) but guarantees the indexer can never see a different set of files than browsing does — one traversal implementation, not two to keep in sync.
- **ffprobe's `format_name` is stored verbatim** (e.g. `"mov,mp4,m4a,3gp,3g2,mj2"` for most MP4s) rather than normalized to a single canonical container name. Deferred until a phase actually displays it — normalizing without a concrete UI need risks guessing wrong.
- **Thumbnail worker priority uses `nice`, not `syscall.Setpriority`.** Both target Docker's alpine/Linux and local macOS dev; `nice` is a plain external-command wrapper available on both (busybox provides it in alpine) and needs no per-OS Go build files. Its absence degrades to normal priority rather than failing.
- **Thumbnail failures aren't auto-retried**, only on the next file change (mirrors the Phase 2 ffprobe-failure precedent) or an explicit retry/rebuild (Phase 5's clear/rebuild controls — see "Hardening and quality of life" above).
- **Codec compatibility uses simplified codec strings** (e.g. `avc1.42E01E` for any H.264 stream), not exact profile/level from ffprobe (which isn't currently captured). `canPlayType()` can be conservative with an inexact string, but the badge only fires on a confident `''` response, so this only risks under-flagging, never hiding a playable file.
- **`internal/thumbnail` renamed to `internal/preview`** in Phase 4, to house both thumbnail and sprite generation under one Manager/one worker pool (see "Preview sprites" above) rather than two independently-bounded pools.
- **Sprite frames are extracted sequentially, not simultaneously**, despite being slower per-invocation-count — see "Preview sprites" above for the OOM failure this specifically avoids. Kept as one ffmpeg call for the final grid assembly (reading back small PNGs), so it's still "not one process per frame" in spirit, just not in the literal single-invocation sense the Phase 4 assignment first assumed.
- **Non-passive touch listeners attached manually**, not via Svelte template attributes. `ontouchmove={...}`/`ontouchend={...}` compile through Svelte 5's event delegation, which registers touch listeners as passive by default — `preventDefault()` inside them is silently ignored. Any future touch handler that needs to block scroll or suppress the post-touch click needs the same manual `addEventListener(..., {passive:false})` treatment, not the template attribute.
- **Remux eligibility uses file extension, not ffprobe's `format_name`**, for the container check — see "Container remux" above; `format_name` can't distinguish MKV from WebM.
- **Remux is pre-generated and cached, never live**, resolving the "seeking during a live remux" open question from the original Phase 6 placeholder by avoiding live remuxing entirely rather than designing more complex streaming logic around it — see "Container remux" above.
- **`.ts` recognized as a streamable extension in this phase** (`internal/media/video.go`, `video/mp2t`), not earlier — MPEG-TS isn't natively playable by any major browser via a plain `<video>` element regardless of its codecs, so recognizing it before there was a remux path to make it playable would have just added a dead-end extension.
- **Root discovery and settings-override merging are two separate functions** (`config.DiscoverRoots`, `settings.MergeRoots`), not one — keeps `internal/config` from needing to import `internal/settings` (avoiding a cycle, since `settings` already imports `config` for the `Root` type) and keeps pure filesystem discovery testable without any settings storage involved.
- **No server-side session table.** A session is a signed expiry timestamp (HMAC-SHA256, keyed by `sessionSecret`); rotating the secret invalidates every session at once. Simpler than a revocation list, at the cost of being unable to invalidate a single session in isolation — an acceptable tradeoff for this app's threat model (see "Onboarding, settings, and an access gate" above).
- **90-day session lifetime**, chosen deliberately per the assignment's own guidance rather than a shorter "security-conscious" default — the actual security boundary is Tailscale/private-LAN, not this cookie, so a long-lived session is pure convenience with no meaningful security cost.
- **No `Secure` cookie flag.** Many people reach this app over plain HTTP directly on their tailnet, not through `tailscale serve`; Tailscale already encrypts the transport regardless. Requiring `Secure` would silently break login for them.
- **`GET /api/health` stays public**, the one deliberate exception to "every route requires a session" — Docker's `HEALTHCHECK` and external monitoring can't authenticate. Initially wrapped in the auth middleware like everything else during development (which would have made the container report unhealthy forever); caught by a regression test before shipping, not by a real failure.
- **bcrypt (`golang.org/x/crypto/bcrypt`) is the one new external dependency this phase adds** — justified the same way `modernc.org/sqlite` already is (a small dependency surface, not zero dependencies at any cost): there's no stdlib password hash, and this is as close to "stdlib-blessed" as Go gets for it.
- **Root promotion uses the filesystem device ID (mount boundary), not "every subdirectory is a root."** A real deviation from the original design (which started from "each immediate subdirectory is a root") made after real usage against a real single-mount deployment showed the original design fragmenting one library into several disconnected ones. See "Root auto-discovery" above.
- **`config.Root` gained a `HiddenChildren` field**, a deviation from an earlier explicit "don't change that type" instruction — necessary once "main" could overlap with promoted roots' filesystem paths; the alternative (a separate side-channel keyed by root ID, threaded through every `Browse` caller) was more invasive for no real benefit.
- **Tag OR-filtering is done in Go, reusing the tag batch-fetch already needed for display**, not a second SQL query — see "Tags and Recently Added" above. A `Store.FilterByAnyTag` SQL method was written, then removed once this redundancy was noticed.
- **`first_indexed_at_unix` is a separate column from `indexed_at_unix`**, set once across all 8 row-creating upsert paths and never updated after — "recently added" must mean first-seen, not last-reindexed. See "Tags and Recently Added" above.
- **`TagPicker` gained an `align` prop (`'start' | 'end'`, default `'end'`)** after a real mobile-viewport check found the default right-aligned popover positioning pushed off-screen when the trigger button sits near a narrow container's left edge (Watch page, bulk-select toolbar). Not caught by any automated check — only by opening the popover at phone width and reading its `getBoundingClientRect()`.
- **Every FFmpeg generation job now runs under its own bounded `context.WithTimeout`**, not the server's whole-lifetime `baseCtx` directly — see "Reliability fix" above. A single stalled invocation could previously hold a worker slot forever; the fix bounds worst-case job duration without adding any new failure-handling path (a timeout just fails through the existing `SetThumbError`/etc. error recording).
- **Failed thumbnails/sprites/remuxes are now automatically retried, up to `maxAutoRetries` (3), on every scan** — a deliberate, bounded reversal of the earlier "permanent failure isn't retried until the file changes or an explicit manual retry" design, after a real deployment hit a batch of environmental failures (a UID/permissions mismatch) that then sat stuck forever. Unlike an unbounded retry-forever policy, a file that's genuinely unable to succeed (verified against a real case: an audio-only `.mp4` with no video stream) still stops being retried after 3 attempts, not held in an infinite loop.
- **`nice -n 15` CPU-priority throttling on FFmpeg jobs was briefly removed by another session, then reverted** — it doesn't address a stuck-job problem (doesn't reduce total work, just raises scheduling priority) and directly contradicts this project's explicit Phase 3 "low CPU priority" requirement. See "Reliability fix" above for why the per-job timeout, not a priority change, was the actual fix.
